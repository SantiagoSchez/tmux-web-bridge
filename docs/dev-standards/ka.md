# The koalarnes harness

What the koalarnes plugin (1.0.0) gives this project, and the workflow it enforces. Generated by the plugin from `.claude/ka.json`: after a plugin upgrade run `/ka:update-harness`, after a configuration change run `ka sync` on the branch that changes it, and never edit this file. `ka sync` refuses to write on `master`.

## The harness's files

- [`.claude/ka.json`](../../.claude/ka.json): the project's configuration (layers and their commands, branches, worktrees, languages, tracker, catalogue, checks). Every skill and `ka` command reads it; `ka config` prints it merged with the defaults.
- [`.claude/rules/ka-mandatory-steps.md`](../../.claude/rules/ka-mandatory-steps.md): what every `tasks.md` must include, with each layer's test, typecheck and lint commands; loaded into every turn.
- This document.
- `.claude/ka.lock.json`: what `ka sync` generated, so it can update what nobody edited.

The generated files are rewritten by `ka sync`; the standards documents, `AGENTS.md` and the layer agents belong to the project. `ka sync` brings one of those up to date only while it still holds exactly what the harness generated, and reports it `OUTDATED` once the team edited it and what the harness generates for it changed (the plugin's template or the project's configuration).

## Skills

The plugin's skills are `/ka:<name>`. For the tasks they cover they take precedence over any personal skill with the same purpose.

| Skill | Use it to |
|---|---|
| `refine` | Turn a work item into an implementation-ready scope. |
| `git-worktree` | Create, enter and remove the worktree each branch lives in. |
| `tdd` | Implement a behaviour test-first (red, green, refactor). |
| `commit` | Commit with Conventional Commits and push the branch; open the pull request when asked, and record its number in the changelog entry. |
| `changelog` | Record the branch's changelog entry (`ka changelog add`). |
| `update-docs` | Patch the standards documents from the branch diff. |
| `audit-docs` | Read every standards document against the code and propose what to delete (dead, false or redundant lines), what to move to the right document and the missing entries of the standards index. |
| `update-features` | Regenerate the feature catalogue from a capability spec. |
| `adversarial-review` | Red-team a change before it is archived. |
| `review-pr` | Review a pull request against these standards. |
| `typescript-react-reviewer` | Review TypeScript + React code (`review-pr` applies it). |
| `release` | Compile the changelog into a version, tag it and release it. |
| `explain`, `show-spec-working` | Explain a piece of code; trace a spec to the code and tests behind it. |
| `code-auditing`, `meta-prompt`, `writing-skills` | Audit code quality; sharpen a request; write a project skill. |
| `init-harness` | Set the harness up in a project that does not have it yet (manual only). |
| `update-harness` | Bring the harness up to date after a plugin upgrade or a configuration change, in a branch of its own. |

Project skills live under `.claude/skills/`. The `/opsx:*` commands come from the OpenSpec CLI.

`adversarial-review` and `review-pr` run in a context of their own, on `opus`, the model of `claude.reviewModel`, through the agent `.claude/agents/ka-reviewer.md`: they read the change from disk and from the pull request, and do not see the conversation. A reviewer that wrote the code reads it as it meant it, so the review never runs in the session that wrote it.

## Agents

| Agent | Use it to |
|---|---|
| `ka:analyst` | Get a second opinion on a decision that is costly to get wrong, from the most capable model in a fresh context. Ask for it ("discuss it with the analyst") or mention it with `@`. It sees nothing of the conversation: the request must carry the decision, the options, the constraints and the files. |
| `ka-evaluator` | Score the suggestions of a finished review loop from 0 to 10, once per pull request, on `opus` (`pullRequests.review.evaluatorModel`). `ka sync` writes it to `.claude/agents/`; the review loop of the rule calls it. |

The developer agent of each layer lives under `.claude/agents/` and belongs to the project. Each changes only its layer and reports what the other layers need to whoever called it. A project file named like one of the plugin's agents (`.claude/agents/analyst.md`) replaces it, for instance to set another `model`.

## MCP servers

The plugin runs two MCP servers, whose credentials come from each developer's environment, never from the project:

- `bitbucket` (`mcp__plugin_ka_bitbucket__*`): pull requests, comments, tasks, pipelines and Downloads. Needs `BITBUCKET_USERNAME` and `BITBUCKET_API_TOKEN`.
- `trello` (`mcp__plugin_ka_trello__*`): boards, lists and cards. Needs `TRELLO_API_KEY` and `TRELLO_TOKEN`.

## The OpenSpec pipeline

Every change starts on its own branch, in its own worktree (`/ka:git-worktree`). Up to "artifacts ready" there are two alternative routes:

- **Route A, fast path** (the scope is known upfront): `/ka:refine` → `/opsx:propose`.
- **Route B, exploratory path** (the scope is fuzzy, or you want to control each artifact): `/ka:refine` → `/opsx:explore` → `/opsx:new <change>` → `/opsx:continue` (proposal) → `/opsx:continue` (specs) → `/opsx:continue` (design) → `/opsx:continue` (tasks).

From there both routes share the same trunk:

`/opsx:apply` → `/opsx:verify` (+ `/ka:adversarial-review` when the scope is broad: see the opt-in steps of the rule) → `/ka:commit` → GitHub pull request → `/ka:review-pr`, recorded with `ka review-rounds record` → *if blockers are open:* the agent edits the affected artifacts → `/opsx:apply` → `/opsx:verify` → `/ka:commit` → `/ka:review-pr` again, at most 3 rounds before the user decides → *when `ka review-rounds gate` passes:* the `ka-evaluator` agent scores the suggestions, and those worth a work item are offered as follow-ups → `/ka:update-features` (when a requirement changed) + `/ka:commit` → **human review of the pull request**, or the user takes it as good without one → `/opsx:archive` → `/ka:commit` → the agent merges into `master` (`squash`) → on the user's go-ahead, the work item is closed with a link to the pull request → on the user's go-ahead, the worktree and its local branch are removed.

- `/opsx:explore` only thinks: it reads code, compares approaches and sketches tradeoffs; it never writes application code.
- `/opsx:continue` creates the **next** artifact of a new change. It never amends artifacts: after review findings or late change requests, the agent edits the artifacts directly and re-implements, so the archived spec matches the code.
