# The koalarnes harness

What the koalarnes plugin (0.3.2) gives this project, and the workflow it enforces. Generated by the plugin from `.claude/koalarnes.json`: run `ka sync` after a plugin upgrade or a configuration change, never edit this file.

## The harness's files

- [`.claude/koalarnes.json`](../../.claude/koalarnes.json): the project's configuration (layers and their commands, branches, worktrees, languages, tracker, catalogue, checks). Every skill and `ka` command reads it; `ka config` prints it merged with the defaults.
- [`.claude/rules/koalarnes-mandatory-steps.md`](../../.claude/rules/koalarnes-mandatory-steps.md): what every `tasks.md` must include, with each layer's test, typecheck and lint commands; loaded into every turn.
- This document.
- `.claude/koalarnes.lock.json`: what `ka sync` generated, so it can update what nobody edited.

The three generated files are rewritten by `ka sync`; the standards documents, `AGENTS.md` and the layer agents belong to the project. `ka sync` brings one of those up to date only while it still holds exactly what the harness generated, and reports it `OUTDATED` once the team edited it and the plugin's version changed.

## Skills

The plugin's skills are `/koalarnes:<name>`. For the tasks they cover they take precedence over any personal skill with the same purpose.

| Skill | Use it to |
|---|---|
| `refine` | Turn a work item into an implementation-ready scope. |
| `git-worktree` | Create, enter and remove the worktree each branch lives in. |
| `tdd` | Implement a behaviour test-first (red, green, refactor). |
| `commit` | Commit with Conventional Commits, push, open the pull request. |
| `changelog` | Record the branch's changelog entry (`ka changelog add`). |
| `update-docs` | Patch the standards documents from the branch diff. |
| `update-features` | Regenerate the feature catalogue from a capability spec. |
| `adversarial-review` | Red-team a change before it is archived. |
| `review-pr` | Review a pull request against these standards. |
| `typescript-react-reviewer` | Review TypeScript + React code (`review-pr` applies it). |
| `release` | Compile the changelog into a version, tag it and release it. |
| `explain`, `show-spec-working` | Explain a piece of code; trace a spec to the code and tests behind it. |
| `code-auditing`, `meta-prompt`, `writing-skills` | Audit code quality; sharpen a request; write a project skill. |
| `harness-init` | Set the harness up, or update its configuration. |

Project skills live under `.claude/skills/`. The `/opsx:*` commands come from the OpenSpec CLI.

## MCP servers

The plugin runs two MCP servers, whose credentials come from each developer's environment, never from the project:

- `bitbucket` (`mcp__plugin_koalarnes_bitbucket__*`): pull requests, comments, tasks, pipelines and Downloads. Needs `BITBUCKET_USERNAME` and `BITBUCKET_API_TOKEN`.
- `trello` (`mcp__plugin_koalarnes_trello__*`): boards, lists and cards. Needs `TRELLO_API_KEY` and `TRELLO_TOKEN`.

## The OpenSpec pipeline

Every change starts on its own branch, in its own worktree (`/koalarnes:git-worktree`). Up to "artifacts ready" there are two alternative routes:

- **Route A, fast path** (the scope is known upfront): `/koalarnes:refine` → `/opsx:propose`.
- **Route B, exploratory path** (the scope is fuzzy, or you want to control each artifact): `/koalarnes:refine` → `/opsx:explore` → `/opsx:new <change>` → `/opsx:continue` (proposal) → `/opsx:continue` (specs) → `/opsx:continue` (design) → `/opsx:continue` (tasks).

From there both routes share the same trunk:

`/opsx:apply` → `/opsx:verify` → `/koalarnes:adversarial-review` → `/koalarnes:commit` → GitHub pull request → `/koalarnes:review-pr` → *if findings:* the agent edits the affected artifacts → `/opsx:apply` → `/opsx:verify` → `/koalarnes:commit` → `/koalarnes:review-pr` again → *when clean:* `/koalarnes:update-features` (if user-visible) + `/koalarnes:commit` → **human review of the pull request** → *when the reviewer approves:* `/opsx:archive` → `/koalarnes:commit` → the reviewer merges into `master`.

- `/opsx:explore` only thinks: it reads code, compares approaches and sketches tradeoffs; it never writes application code.
- `/opsx:continue` creates the **next** artifact of a new change. It never amends artifacts: after review findings or late change requests, the agent edits the artifacts directly and re-implements, so the archived spec matches the code.
