# OpenSpec — mandatory task steps

Every `tasks.md` under `openspec/changes/<change>/` MUST include the steps below. The agent executes them; the human does not. A task is marked `[x]` only after the agent has run what it requires and produced what it describes.

The steps are numbered in the order they sit in a `tasks.md`: step 1 is the first task group; step 2 comes before the change's own task groups, which are step 3; steps 4 to 9 follow, in that order. The review loop (`/opsx:verify`, `/koalarnes:adversarial-review`, `/koalarnes:commit`, the pull request and `/koalarnes:review-pr`) runs between step 6 and step 7.

**The plugin's skills take precedence.** For the tasks the koalarnes plugin covers (refining work items, worktrees, commits, changelog entries, PR reviews, Playwright E2E, test-driven development, releases, the feature catalogue, the user manual), use its `/koalarnes:<name>` skills, never a personal or other skill with the same purpose: they read this project's configuration. If the user names such a skill (`/commit`, `/git-worktree`, `/review-bitbucket-pr`, `/playwright-e2e`…), run the plugin's and say so in one line.

## Step 1 — Create the branch (always first)

Branch from `master`. Prefixes: `feature/` (features), `bugfix/` (bug fixes), `hotfix/` (production hot-fixes), `chore/` (internal chores with no work item).

Names mirror the GitHub issue: `<prefix><issue number>-<kebab-case title>`. The slug is the issue title in lower case, ASCII only (accents stripped), words joined with `-`. Example: issue `#276 — Add Catalan as a generation language` → `feature/276-add-catalan-as-a-generation-language`.

**Every branch lives in its own worktree.** Create it with `/koalarnes:git-worktree create <prefix><name>`: the plugin's hooks branch it from `origin/master`, copy the ignored local files (`.worktreeinclude`, else `.env*`) and run `pnpm install --frozen-lockfile` in it, and the session moves into it. Never `git checkout -b` in the main checkout, which stays on `master`. A worktree name holds at most 64 characters: shorten the slug, keep the prefix and the work item's number.

## Step 2 — Review the existing tests (mandatory)

Before changing behaviour, read the tests of every module the change touches and confirm they still describe the intended behaviour. If they describe outdated behaviour, update or add tests **before** the implementation lands.

Every new or rewritten test follows the project's testing standards (linked from `AGENTS.md`): written at the cheapest level that runs the behaviour for real, mocking only true boundaries, asserting outcomes, and seen failing before it is marked done. A test the change touches that matches one of their refused patterns (a copy of the code under test, a mock echo, a restated constant, a tautology) is fixed or moved in the same change.

Output: one line per inspected module saying "tests up to date" or "tests updated/added in this change".

## Step 3 — Implement the change's tasks

The change's own task groups, written by `/opsx:propose` (or the last `/opsx:continue`) from the proposal, design and specs, and executed by `/opsx:apply`, each behaviour test-first (`/koalarnes:tdd`).

## Step 4 — Run tests, typecheck and lint (mandatory)

The agent MUST run these for every layer the change touches and verify they pass. Never delegate to the human.

- **server**:
  - test: `pnpm --filter server test`
  - typecheck: `pnpm --filter server typecheck`
- **web**:
  - typecheck: `pnpm --filter web typecheck`
- **trello-extension**:
  - test: `pnpm --filter trello-extension test`
  - typecheck: `pnpm --filter trello-extension typecheck`
- **host-kit**:
  - test: `scripts/test-kit-update.sh`

Also run the project checks:

- feature catalogue: `ka features-check` (must pass)

When a type or lint error surfaces, fix the root cause; do not silence the rule. The plugin's hooks format and lint each edited file and typecheck when the agent stops, best effort; they do not replace this step.

## Step 5 — Update the documentation and the changelog (mandatory)

When any of these changed, update the relevant standards document (`/koalarnes:update-docs`) and add a changelog entry with `/koalarnes:changelog`:

- An API contract (new, removed or changed endpoint or payload).
- The data model (new entity, removed field, migration).
- A message or job payload.
- An environment variable (new, renamed, removed).
- A flow visible to the end user.

When the change introduces a pattern future contributors should follow, add it to the relevant standards document.

## Step 6 — Update the feature catalogue (mandatory if user-visible)

If the change adds, modifies or removes a feature visible to end users or to the product team:

1. Run `/koalarnes:update-features <change-name>` to draft the update of `docs/FEATURES.md` from the capability spec, review it and apply it.
2. Run `ka features-check`. Exit code MUST be 0.
3. Commit it immediately with `/koalarnes:commit`. The catalogue sync MUST land in the pull request before the human review (step 8).

Each section of the catalogue carries the anchor of the requirement it describes, right after its heading:

```markdown
### <heading>
<!-- capability: <cap-slug>; requirement: <req-slug> -->
```

`<req-slug>` is the kebab-case of the Requirement name as it appears in the spec. `ka features-check` reports any drift between the two sides.

## Step 7 — Green E2E pipeline run (mandatory before human review)

The project has no E2E suite; this step does not apply. Record that in the task.

## Step 8 — Human peer review (mandatory before archive)

After `/koalarnes:review-pr` comes back clean, the catalogue sync of step 6 is committed and step 7 is green, **another developer MUST review the pull request** before the author archives.

- The author does NOT run `/opsx:archive` until the reviewer approves.
- Reviewer findings are handled exactly like the automated review's (see below); the cycle reopens until the reviewer approves.
- When the reviewer approves, the author runs `/opsx:archive`, then `/koalarnes:commit` to push the archive moves into the same pull request.
- The reviewer who approved merges the pull request.

## Step 9 — features-check before the archive (mandatory)

`/opsx:archive` does not run the catalogue linter. The agent MUST run it as the last task before archiving:

```bash
ka features-check
```

Exit code MUST be 0; fix any drift before archiving.

## Opt-in steps

Not mandatory; add them when the scope warrants:

- **Manual endpoint testing** with `curl` for new or changed HTTP endpoints: the main methods plus the obvious error cases (400, 401, 404, 422); restore the data after each mutating call.
- **Adversarial review** (`/koalarnes:adversarial-review <change>`) for changes with a broad blast radius: message or job payloads, dependency wiring, migrations on large tables.
- **Boot smoke test** for changes to dependency-injection wiring or application bootstrap: start the app, wait for its ready log line, stop it. Wiring errors do not surface in typecheck or unit tests.
- **Payload call-site audit** for a change to a message or job payload: list every producer and consumer and confirm each was updated.

## After `/opsx:apply` and before `/opsx:archive`: change requests

Findings of `/koalarnes:review-pr`, of the human reviewer, or requests arriving from elsewhere (chat, stakeholders, design feedback) follow the same steps. **Do not patch the code directly.**

1. The agent edits the affected artifacts (`proposal.md`, `design.md`, `tasks.md`, `specs/**`) directly so they describe the corrected behaviour. The user may hand-edit typos only.
2. The agent re-implements against them with `/opsx:apply`.
3. The agent re-verifies with `/opsx:verify` (and `/koalarnes:adversarial-review` if the scope warrants).
4. The agent commits with `/koalarnes:commit` and re-runs `/koalarnes:review-pr` on the same pull request.

`/opsx:continue` is not for this: it creates the next artifact of a new change; amendments are direct edits. The archived spec must match production exactly.
